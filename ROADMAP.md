# Packr roadmap

Last updated 2026-10-26. Written from the three starting artifacts: the knowledge-engine demo notebook,
`Packr_dataset_merge_v3.ipynb`, and `Packr_Presentation.pptx`.

## 1. Where things stand

* **Engine**: ported from the demo into `packr.engine`. It reproduces the demo's results (chips -> MetPET / CPP,
  strawberries -> micro-perforated BOPP) and is covered by tests. Its rule thresholds and material values are
  placeholders, not calibrated.
* **Data layer**: TRANSMAT reshape, unit normaliser and spoilage loader are built and tested on fixtures that copy the
  row formats seen in the merge notebook. They have **not been run on the real files** (the build workspace could not
  reach the download hosts).
* **Not started**: simulation, success-rate model, ML, app.

## 2. What the merge notebook actually produced

1. **`packaging_materials` is not a materials table.** It is the raw TRANSMAT annotation table: 1,776 rows, one per
   extracted entity (a number, a unit, a name), from 49 papers, with 13 `target` types. `COLUMN_MAP` (cell 15) is empty,
   so no renaming or reshaping ever happened.
2. **Cells 29, 30 and 37 fail** with `KeyError: 'o2_permeability'` (and `_median`) because those columns never existed.
3. **The cross join is meaningless.** 27 commodities x 1,776 annotation rows = 47,952 "candidate pairs", but each right-hand row is
   a fragment such as a unit or a temperature, not a material. The compatibility rule then returned **0 rows**
   (cell 28 prints `(0, 23)`), so the exported `commodity_packaging_map.csv` is empty. That rule also compared a
   thickness-normalised permeability coefficient to 1000, which is only meaningful after unit conversion.
4. **The spoilage dataset has no packaging column.** 10,995 rows, four fruits (banana, orange, pineapple, tomato), all recorded
   at roughly 23-25 C and 92-95 % RH, with about 50 % labelled good for every fruit. It can say how sensor readings relate to a
   good/bad label for those fruits. It cannot say anything about which packaging works.
5. **The two sources share no key.** TRANSMAT says nothing about foods and the spoilage data says nothing about packaging, so a
   join cannot connect them. Compatibility has to come from rules and simulation.
6. **The commodity seed is all fresh produce** (27 rows), with respiration rates "near common retail/transport temperatures" but
   no per-row reference temperature, which matters because respiration roughly doubles to triples per 10 C. It has no moisture, fat or pH, and no
   processed foods, so potato chips (the original example) have no commodity row.

What the notebook got right: choosing the `-all` consensus file, and its own caveats about the seed table being compiled
midpoints. Those caveats are preserved in `data/README.md`.

## 3. What each source can and cannot do

| Source | Provides | Does not provide | Role |
|---|---|---|---|
| TRANSMAT | gas and vapour permeability values with units, test temperature, thickness, material names, as separate entities | which value belongs to which material; any food | material barrier table, after association (phase 1) |
| Spoilage sensors | temperature, RH, CO2, light -> good/bad, four fruits | packaging; shelf life in days | optional spoilage-risk feature or sanity check, never outcome labels |
| Literature seed (27 produce) | respiration, ideal T and RH, typical shelf life | respiration reference temperature; composition | commodity table |
| USDA FoodData Central (not used yet) | moisture and fat for many foods, including snacks | pH, respiration | fill composition |
| Open Food Facts (in the deck, not used yet) | real packaging per product category | barrier values | check recommendations against market practice |

**Consequence:** no available source links a packaging specification to a measured shelf-life outcome. The labels for any
success-rate model must come from simulation, calibrated against a small set of literature pairings (section 6).

## 4. Deck versus build

| Deck step | State |
|---|---|
| Build the knowledge base (commodity profiles + material barrier data) | Produce profiles carried over; material table is placeholder |
| Engineer features (respiration at storage temperature) | `units.q10_adjust` exists; needs reference temperatures per commodity |
| Train models (classify material, predict OTR, WVTR, thickness) | Needs training data: generated by engine + simulation (phase 4), not by the sources above |
| Apply domain rules | Done in `packr.engine`; thresholds to calibrate |
| Extensions (shelf life, sustainability, cost, QR, eco picks) | Phase 5 |

Gap: the deck's data sources cover fresh produce. Your chips example (dry, fatty snack) has no data source yet.

## 5. Phases

**Phase 1: real data in.** Needs `goldenTRANSMAT-all.tab` and `Dataset.csv` (see `data/README.md`).
* Run `python -m packr.build_tables`; read `data/processed/audit.txt`; extend `units.py` for the most common unit failures it lists.
* Solve material association: link permeability values to named materials. Start with papers that name a single packaging material; hand-label the most useful remaining papers. Output `materials_from_transmat.csv` with the source DOI on every row.
* Fill `moisture_pct`, `fat_pct` from FoodData Central and `ph` from literature for every commodity; add snack rows if snacks are in scope.
* Record the temperature each respiration value applies to, checking all 27 against USDA Handbook 66 directly.
* Done when: at least 20 real material rows with DOIs, all commodities complete, and at least 80 % of permeability rows converted (the rest explained).

**Phase 2: engine v1 on real data.**
* Replace placeholder materials; offer a thickness range using `materials.required_thickness_um`, which first needs `min_gauge_um` and `max_gauge_um` per material (today it returns the bare mathematical minimum, e.g. 0.005 um for EVOH, which no film can be).
* Temperature and RH dependence of permeability (EVOH loses barrier at high RH; Arrhenius for temperature).
* MAP from first principles: respiration -> required OTR needs pack mass and film area as inputs.
* Rules for frozen storage (the input is accepted today but unused).
* Done when: outputs include a thickness range and the placeholder note no longer appears.

**Phase 3: calibrate and simulate.**
* Per-category kinetics: dry fatty snacks (moisture uptake to a critical moisture, oxidation index), fresh produce (O2/CO2 gas balance).
* Monte Carlo over temperature, RH, seal quality and material tolerance -> success rate and failure mode per scenario.
* Calibrate against the pairings in section 6, adjusting the kinetics constants and the rule thresholds.
* Done when: the simulation reproduces the pass/fail direction of at least three literature pairings.

**Phase 4: ML.**
* Synthetic dataset from phase 3, split by commodity group (hold out a whole category).
* Gradient-boosted trees with heads for success probability and shelf life, plus the deck's targets (material class, OTR, WVTR, thickness). FT-Transformer as an optional comparison.
* Done when: held-out-category performance is reported against the rules-only baseline.

**Phase 5: app and extensions.** API (FastAPI) and a web or Flutter front end; sustainability, cost, QR traceability.

## 6. Calibration pairings to start from

1. **Caramelised cookies in three films** (Hasselt University document server, handle 1942/33777): PP film (OTR 1307 cc/m2/d,
   WVTR 5 g/m2/d) and acryl-coated PVdC/PP (OTR 21.8, WVTR 4.2) had compromised texture after 6 months at 22 C and 50 % RH,
   while metallised PP (OTR 31.2, WVTR 0.4) extended acceptability. If the cookies fall in the engine's medium moisture-gain tier
   (WVTR <= 5 for shelf life over 90 days), the engine would accept the 4.2 film that the study found compromised. That is a first sign
   the tier may be too lenient. Confirm the cookie composition and WVTR test conditions from the paper before acting on it.
2. **Strawberry cardboard trays** (Pigneres et al., B2FIND dataset of OTR/CO2TR targets and headspace modelling): a worked example for
   the fresh-produce side.
3. **Norner barrier calculator**: an independent check of the laminate OTR/WVTR series model in `structures.py`.

## 7. Decisions needed

1. **Commodity scope.** Fresh produce only (matches the deck and the data), or produce plus dry fatty snacks (matches your chips example, needs FoodData Central rows and a second kinetics model)? Recommendation: both, as two categories.
2. **Team and deadline.** The deck says "our specialization project". Is anyone else working on it, and what is the demo or submission date? That decides whether phase 5 stays in scope.
3. **Raw files.** Send `goldenTRANSMAT-all.tab` and `Dataset.csv`, or allow the Dataverse and USDA API hosts for the build workspace, so phase 1 can run on real data.

## 8. Known weak points

* Risk and requirement thresholds are unvalidated starting points. Material values are placeholders.
* Recyclability is "single polymer family" only. Laminate properties ignore adhesive and tie layers and humidity effects.
* The cost index is unitless and ignores thickness.
* Any success-rate figure will be only as good as the phase 3 calibration. State that in the report.
* TRANSMAT material association is unsolved; the parser's repair of damaged characters is a heuristic until checked on the real file.
